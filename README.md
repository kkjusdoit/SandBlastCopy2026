# Unity 竖屏版《流沙俄罗斯方块》

基于 Unity 6 URP 实现的手机竖屏版《流沙俄罗斯方块》原型项目。

这不是传统“满行消除”的俄罗斯方块，而是结合了：

- Tetromino 下落、移动、旋转
- 锁块后转化为细粒度“沙子”
- 沙粒以元胞自动机规则持续流动
- 仅当同色连通区域从左边界贯通到右边界时触发消除

当前仓库包含一版可运行的 Unity 原型，用于验证核心玩法、沙粒模拟、特殊消除规则和移动端竖屏 UI。

- 锁定后将块体映射为细粒度沙网格

## 实施计划

### Summary

在当前 Unity 6 URP 空项目中实现一版手机竖屏、高完成度单机原型，完整还原教程中的核心规则：

- Tetromino 形状生成、移动、旋转、下落
- 锁定后将块体映射为细粒度沙网格
- 沙粒按元胞自动机规则持续流动
- 仅当同色连通区域从左边界贯通到右边界时触发消除
- 提供完整可玩流程：开始界面、对局、得分、失败、重开、Next 预览、音效与基础反馈

### Key Changes

#### Core Simulation

- 建立双网格系统：
  - 粗网格用于当前活动块的生成、移动、旋转、落地判定
  - 细网格用于沙粒占据、流动与消除检测
- 设定固定换算系数 `grainScale`，每个粗格映射为 `grainScale x grainScale` 个沙粒单元。
- 当前活动块仅在粗网格层存在；落地后一次性写入细网格并转为静态沙粒。
- 碰撞检测按活动块每个粗格映射到细网格覆盖区判断，命中已占据沙粒或越界即视为碰撞。
- 沙粒更新采用自下而上、每行随机列顺序的元胞自动机更新：
  - 下方为空则下落
  - 否则检测左下、右下
  - 双侧都可走时随机选一侧
- 消除检测按颜色分组，从左边界出发做 4 邻域连通搜索；某颜色连通块若接触右边界，则整组进入消除队列。
- 消除流程分为“标记 -> 闪烁/高亮 -> 清空 -> 重力再结算”，允许一次消除后继续触发后续连锁。

#### Game Rules And UX

- 首版保留教程规则，不实现传统整行消除模式。
- 首版使用手机竖屏 + 屏幕按钮输入：
  - 左移
  - 右移
  - 旋转
  - 加速下落
- 提供 `Next` 预览，不做 `Hold`。
- 失败条件定义为：新块生成时即与已有沙粒重叠，无法合法出生。
- 计分先按简洁方案落地：
  - 成功消除按消除沙粒数计分
  - 连续消除可加连击倍率
- 对局节奏分阶段提升：
  - 随时间或分数提高下落速度
  - 仅在不破坏沙粒模拟稳定性的前提下加快局势
- UI 范围限定为高完成度单机原型：
  - 标题/开始
  - 游戏主界面
  - 分数/最高分
  - Next 预览
  - 暂停/失败/重开

#### Rendering And Architecture

- 不使用 Rigidbody/Collider 做沙子，不为每个沙粒创建 GameObject。
- 逻辑层使用纯数据网格驱动：
  - 活动块状态
  - 细网格沙粒颜色/占据状态
  - 消除标记状态
- 表现层采用像素颗粒风渲染，优先用单张可写纹理或等价批量渲染方案，把细网格直接绘制到棋盘区域。
- 活动块单独渲染在沙盘上层，保持“落下前是块、落地后变沙”的视觉分层。
- 模块边界明确拆分为：
  - 游戏状态控制器
  - 活动块规则系统
  - 沙粒模拟系统
  - 连通消除系统
  - 棋盘渲染系统
  - UI/输入系统
- 数据结构预留扩展位，后续可加入：
  - 特殊块
  - 关卡目标
  - 道具
  - 不同消除规则模式

### Test Plan

- 活动块在空盘面中可正常左右移动、旋转、软降和自动下落。
- 活动块贴边、贴已有沙堆时，碰撞检测稳定，不出现穿透或错位。
- 不同形状在锁定时都能正确映射到细网格，不丢格、不越界。
- 沙粒落地后会向下、左下、右下扩散，不会静止成不合理悬空结构。
- 同色区域只在“左边界连到右边界”时消除；未贯通时绝不误消。
- 消除后沙粒继续下落，并允许触发后续二次或多次连锁。
- 新块出生被阻挡时正确结束游戏。
- 竖屏按钮输入在真机分辨率下可稳定操作，UI 不遮挡核心棋盘。
- 在目标移动设备上保持可接受帧率，重点验证高沙粒密度局面。

### Assumptions

- 教程中的核心规则按截图内容完整还原：双网格、沙化、4 邻域、左右贯通消除。
- 第一版目标是“高完成度单机原型”，不包含广告、任务系统、签到、商店、联网或排行榜。
- 美术先以程序化像素颗粒风和简洁 UI 为主，不依赖外部商业资源包。
- 首版只做 `Next`，不做 `Hold`。
- 首版以触屏按钮为主，不同时支持手势输入。

## 微信小游戏 WASM 代码分包

### 已知限制：自动函数收集不可靠

本项目不能只依赖 `wasm-code-split` 插件的自动函数收集来决定首包函数。实际真机收集曾长期只增加少量 Unity/C++ 运行时函数，例如：

- `std::__2::__libcpp_relaxed_store`
- `MemoryManager::InitializeMemoryLazily`
- `DynamicHeapAllocator::Allocate`
- `Baselib_SystemSemaphore_CreateInplace`

这些函数并非流沙玩法热路径。若出现“每次运行固定新增 1 个函数”的情况，不要反复生成 profile 分包；插件只要新增数大于 `0` 就可能显示“当前新增函数过多”，该提示不代表收集质量足够。

项目的固定策略是：真机自动收集仅用于补充和验证，核心玩法热函数必须从当前构建的 WASM 符号表中筛选并手动上报。

### 何时必须重新分包

在插件中查看“当前代码 md5”。只要 MD5 与上次 release 分包不同，就不能复用旧分包，必须重新生成 profile 和 release 分包。

- C#、Unity 插件或构建配置变化通常会改变 WASM MD5。
- 纯图片、文案或外部资源变化不一定改变 WASM MD5，但重新导出仍可能覆盖插件生成的分包文件。
- 每次 Unity 重新导出后，都应重新检查 MD5 和分包状态。
- 旧的函数清单不能直接假定有效；IL2CPP 函数名中的哈希可能变化，必须对新符号表重新校验。

### 标准分包流程

1. 从 Unity 导出用于收集的 profile 包到：
   `/Users/linkunkun/WeChatProjects/SandFlow-WasmCollection/minigame`
2. 在微信开发者工具中打开上述 `minigame` 目录，再启用 WASM 代码分包。启用后不要再次从 Unity 覆盖导出。
3. 若插件允许，选择上一次稳定 release 版本进行增量分包。
4. 等待后台预处理完成。所有“生成 profile/release”按钮都只点击一次，禁止连点或重试叠加任务。
5. 使用 Unity 菜单 `Flow Sand/Build/Export WASM Collection Package` 导出时，构建工具会自动扫描当前 `webgl.wasm.symbols.unityweb`，更新 IL2CPP 函数哈希，并在小游戏目录生成 `FlowSand-Wasm-HotFunctions.txt`。若只需重新扫描已有导出，使用 `Flow Sand/Build/Generate WASM Hot Function List`。
6. 点击插件中的“选择函数名文件手动上报”，选择 `minigame/FlowSand-Wasm-HotFunctions.txt`。
7. 检查分包日志，必须出现类似 `[reportFuncNameList] 上报函数数量: 35`，且不得出现“未找到 symbols 中的 key”。
8. 等后台“新增收集函数个数”更新后，只点击一次“生成 profile 版分包”。
9. 确认 profile 首包函数中已经包含 `FlowSandGameController`、`FlowSandMatchCoordinator`、`FlowSandBoard`、`FlowSandBoardRenderer` 等真实玩法函数。
10. Android 使用真机调试二维码，iOS 使用预览二维码，重新扫码当前 profile 版本，覆盖冷启动、开局、移动、旋转、软降、沙粒下落、消除、结算和重开。
11. 对新增函数先查看函数名：玩法热函数需要补充；`std::`、`Baselib`、内存分配或信号量等底层函数可忽略，不能仅因新增数为 `1` 就重新生成 profile。
12. 双端验证通过后，只点击一次“生成 release 版分包”。再次用 Android/iOS 验证 release 版本，最后通过开发者工具右上角“上传”提交代码包。

### 热函数清单

当前仓库中的 [FlowSand-Wasm-HotFunctions.txt](FlowSand-Wasm-HotFunctions.txt) 是热路径选择模板，覆盖：

- `Update` / `LateUpdate` 与可视刷新
- 沙粒模拟、下落、碰撞
- 桥接检测与消除
- 棋盘纹理刷新
- 移动、旋转、软降输入
- HUD 更新

每次 WASM MD5 变化后，必须先确认该文件的每一行仍能在新的 `webgl.wasm.symbols.unityweb` 中精确匹配；若方法哈希变化，应按新符号表重新生成，不能直接上传旧文件。

`FlowSandWeChatBuild` 会自动执行上述匹配：它使用函数名中 `_m<40 位哈希>` 之前的稳定方法名，在新符号表中寻找唯一匹配并更新哈希。缺失、重名或解析失败都会让导出明确报错，避免上传残缺清单。生成结果同时写入仓库模板和当前小游戏导出目录。

### 验收与故障排查

- 分包日志：`minigame/.plugincache/codesplit/log/latest.log`
- 函数名导出：插件中的“获取首包函数和新增函数的函数名”
- 成功的 profile 首包应包含真实 `FlowSand...` 函数，而不应只有 Emscripten、IL2CPP、Baselib 和 C++ 标准库初始化函数。
- 如果出现 `message: not found`，先检查日志中是否在一秒内重复触发了两个 `startsplit`；不要继续连点“重试”。
- 如果长时间停在“下载和压缩分包代码”，检查是否同时轮询了不同 `sub_version`。服务端可能已完成其中一个任务，但界面被旧任务卡住。
- 生成 release 后不要再从 Unity 导出到同一目录，否则会覆盖最终分包产物。
